用 103 句實測，第一版只有 78.6% 準確，抓出來的錯誤幾乎都是「工具說明寫得不夠清楚」造成的混淆（例如「工作管理員」跟「工作排程器」名字太像）。把說明重新寫清楚、多給幾個範例之後，準確率跳到 97.1%，超過原本設定的 95% 目標，而且反應時間還變快了（0.2秒/句）。

First pass on 103 test phrases scored 78.6%; nearly all errors traced back to unclear tool descriptions (e.g. "Task Manager" vs "Task Scheduler" sounding alike in Chinese). Rewriting the descriptions and adding examples pushed accuracy to 97.1% — above the 95% target — while also getting faster (0.2s/phrase).

最新里程碑：整條語音迴圈真的能跑了Latest milestone: the full voice loop actually works

今天把 P0-P3 全部串成一個真正的常駐程式（`src/listen_loop.py`）：對著麥克風說「嗨小助理」會被正確喚醒，講一般電腦操作指令（像「現在幾點」「把音量調到20%」）會被立刻執行；講聲學工程問題（像「我的喇叭低頻聲音怪怪的」）則會由語音助理用講的引導你把問題講清楚，三輪問答後自動幫你整理成一份正式「訂單」送給 AERIS 處理——這整段從語音輸入到送出訂單，都是真的用講的走完，不是打字模擬。

Today P0-P3 got wired into one real background program (`src/listen_loop.py`): saying "Hi Assistant" wakes it up correctly, ordinary commands ("what time is it", "set volume to 20%") execute immediately, and acoustic-engineering questions get a guided voice conversation that ends with a formal order handed to AERIS — the whole thing, start to finish, driven entirely by voice, not typed simulation.

藍圖盤點：補上安全缺口＋文字輸入Blueprint audit: safety gaps closed, text input added

逐節對照原始藍圖檢查已完成的東西，抓到並修正兩個安全性缺口：緊急停止熱鍵原本設錯（不是藍圖規定的 Ctrl+Shift+F12），以及語音講「停止」「取消」原本完全無法打斷流程——兩者都已修正，並用真的語音合成→真的跑辨識引擎的方式驗證過，不是紙上談兵。同時補上文字輸入功能：即時陪伴介面現在打字也能用，跟語音是同一套後端邏輯、效果一樣，不會因為不方便講話就沒辦法用。

Cross-checked everything built so far against the original blueprint, section by section, and found two safety gaps: the Emergency Stop hotkey was wired to the wrong key (should be Ctrl+Shift+F12 per spec), and spoken "stop"/"cancel" commands couldn't interrupt an in-progress flow at all — both fixed and verified with real synthesized speech run through the real recognition pipeline, not just code review. Also added text input: the companion interface now accepts typing, sharing the same backend logic as voice, so it works even when speaking isn't convenient.

補上UI Automation原語：能操作任意應用程式了UI Automation primitives added: can now operate any application

做了一份逐節對照藍圖的詳細進度報告後發現：藍圖明文要求的「切換視窗/點擊按鈕/操作輸入欄位/按組合鍵」這幾個基本操作能力完全沒做，導致AI一直只能操作4個白名單裡的App，碰不到使用者自己開的其他視窗。現在補上了：可以查詢/切換到任意視窗、點擊視窗裡的按鈕（用畫面上的文字定位，不是憑座標亂點）、送出鍵盤按鍵跟組合鍵（例如存檔用的Ctrl+S）。過程中也抓到一個Windows本身的安全限制（背景程式不能隨便搶走視窗焦點）並修好了。

A detailed section-by-section audit against the blueprint found that basic operations it explicitly requires — switching windows, clicking buttons, filling in fields, sending key combos — were completely missing, which meant the AI could only operate 4 whitelisted apps and couldn't touch anything else the user had open. Now added: querying/switching to any window, clicking buttons located by their actual on-screen text (not blind coordinates), and sending keystrokes/combos (like Ctrl+S to save). Along the way, hit and fixed a genuine Windows security restriction that blocks background processes from stealing window focus.

補上多步驟規劃：一句話可以拆成幾個連續動作了Multi-step planning added: one sentence, several chained actions

藍圖最終驗收要求的例子是「找到Downloads裡最新的PDF，打開它，然後把檔名告訴我」——這種話裡包含三個依序動作，而且第二步（開哪個檔案）要等第一步真的執行完才知道答案，原本的系統只能處理一句話對應一個動作。現在補上了：AI會先判斷這句話是不是需要好幾步，如果是，就一步一步來，每一步都用「上一步真正執行後的結果」決定下一步要做什麼，不是自己憑空亂猜檔名。用真實測試（真的建測試檔案）連續驗證4次都正確：找到真正最新的檔案、用真實路徑打開它、正確講出檔名。單一動作的指令（像「現在幾點」）完全不受影響，一樣快。

The blueprint's final acceptance example is "find the newest PDF in Downloads, open it, then tell me the filename" — three chained actions where step two (which file to open) can't be known until step one has actually run. The system used to handle only one action per sentence. Now it decides upfront whether a sentence needs multiple steps, and if so works through them one at a time, each step using the real result of the previous one rather than guessing a filename out of thin air. Verified correct across 4 real test runs (with real test files): found the genuinely newest file, opened it using the real path, correctly reported the filename. Single-action commands ("what time is it") are unaffected and just as fast.

補上記憶跟操作紀錄：查得到「AI記得什麼、做過什麼」了Memory and logging: now you can see what the AI remembers and did

新增了四種記憶（用過的App、用過的資料夾、每個對話的目前狀態、使用者偏好設定），也把操作紀錄補齊成藍圖要求的完整格式（哪次對話、花了多久、失敗原因）。過程中查資料庫時意外發現一個真實問題：「對話紀錄」這張表雖然存在，但實際上從來沒有被寫入過任何一筆資料——找到並修好了，現在語音跟打字兩種輸入方式都會真的記下來。

Added four kinds of memory (apps used, folders used, each conversation's current state, user preferences), and completed the action log to the blueprint's required format (which conversation, how long it took, why it failed). While checking the database, found a real issue: the "conversation history" table existed but had never actually received a single row — found and fixed it; both voice and typed input now genuinely get recorded.

誠實回報：兩項延遲指標測出來沒有達標Honest finding: two latency targets are not met

用真的語音（不是打字）量測「喚醒後多久能聽懂你說的話」，結果是5.4秒左右，比原本設定的1.5秒目標慢很多；整體從喚醒到回覆完成大約6.1秒，也超過3秒的目標。拆解後發現問題不在語音辨識本身（那部分大約1.5秒，正常），而是系統為了「確認你真的講完話了」會刻意多等一段安靜的時間——這是先前刻意做的安全設計（等太短會誤判你話還沒講完就把你打斷），但這次量測第一次把這個取捨的真實代價用數字攤開來看。要縮短這段延遲，需要重新設計「怎麼判斷你講完了」這件事，跟「不要誤判打斷你」互相拉扯，不是調一下參數就能兩全，這點會誠實留在待辦清單裡，不會假裝已經解決。

Measured "how long after wake-up until the system understands you" using real voice (not typed text): about 5.4 seconds, well over the 1.5-second target; end-to-end from wake-up to a finished reply is about 6.1 seconds, over the 3-second target. Breaking it down shows the problem isn't speech recognition itself (about 1.5s, normal) — it's that the system deliberately waits through a stretch of silence to confirm you've actually finished talking. That's an intentional safety tradeoff from earlier work (cutting the wait too short risks interrupting you mid-sentence), but this measurement is the first time the real cost of that tradeoff has been put into numbers. Shortening it means redesigning how "finished speaking" gets detected, which pulls against not interrupting you — not a simple parameter tweak, and it's staying on the honest to-do list rather than being papered over.

重大進展：藍圖P3的驗收測試真的跑通了（並修正了先前一個誤判）Major milestone: the blueprint's P3 acceptance test actually passed (and corrected an earlier misdiagnosis)

藍圖要求的驗收流程「開記事本→輸入Hello→存檔→關閉→重新打開」這次真的完整跑過一次，並且用檔案系統直接驗證內容真的存下來了。過程中發現先前判斷「這台機器沒辦法開某些內建程式」的原因其實搞錯了——真正原因是啟動程式的方式撞到系統裡兩個同名捷徑衝突，換一種更明確的啟動方式後，記事本、小算盤都能穩定開啟。也發現這個新版記事本不接受電腦模擬的鍵盤快捷鍵（連Ctrl+S都沒反應），改成直接點擊選單裡的「存檔」按鈕才成功——這正好印證了當初藍圖堅持「盡量用點擊操作、少用模擬按鍵」這個設計原則是對的。

The blueprint's required test flow — open Notepad, type "Hello", save, close, reopen — actually ran start to finish this time, with the file system itself confirming the content genuinely persisted. Along the way, an earlier diagnosis that "this machine can't launch certain built-in programs" turned out to be wrong — the real cause was a naming conflict in how the program got launched; switching to a more explicit launch method made Notepad and Calculator both open reliably. Also discovered this modern Notepad ignores simulated keyboard shortcuts entirely (not even Ctrl+S worked) — clicking the Save menu item directly succeeded instead. That's a real-world confirmation of why the blueprint insisted on preferring clicks over simulated keystrokes.

接下來的路What's next

P3 — 讓 AI 真的能操作電腦— Let the AI actually operate the computer

目前 AI 只能「說出」它想做什麼，還不能真的去點擊、開啟、關閉東西。這一步會寫程式讓它能安全地操作 Windows（開程式、找檔案、點按鈕），並且在第一次正式對你的桌面環境動手之前，會先讓你看過一次，這是唯一會主動停下來讓你確認的地方。

Right now the AI can only "say" what it wants to do — it can't yet click, open, or close anything. This step writes the code to safely operate Windows (launch apps, find files, click buttons). Before it ever touches your real desktop for the first time, you'll see it happen — the one place I'll deliberately pause for you.

P4 — 安全把關機制— Safety guardrails

分成四個風險等級：看資料（免確認）→ 一般操作（免確認）→ 敏感操作（AI 會先問你）→ 危險操作（一定要你按確認）。同時做一個「操作紀錄本」，記下 AI 做過的每件事，方便回頭查。

Four risk tiers: read-only (no confirmation) → routine (no confirmation) → sensitive (AI asks first) → dangerous (always needs your confirmation). Also builds an audit log recording everything the AI does.

P5 — 看不懂畫面時的備援— Fallback when it can't read the screen

萬一 AI 找不到要點的按鈕，讓一個視覺模型「看」一眼畫面幫忙定位，只在必要時才啟動（省資源）。

If the AI can't locate a button, a vision model looks at the screen to help — only activated when actually needed, to save resources.

P6 — 全部串起來，整體測試— Full integration test

把前面五個階段全部接起來，測整體反應速度跟穩定度，達標才算真正完工。

Everything from the previous five phases wired together, tested for overall speed and stability. Only counts as truly done once it hits the targets.

我在照的原則Principles I'm following

① 本機優先——所有運算能在你這台電腦跑就不假手雲端；只有本機真的做不到才考慮雲端 AI，而且會先跟你講。② 精準度優先於速度——只要你感覺不到延遲，就選比較準的方案。③ 能操作你電腦前一定先讓你看過——這是唯一的停下來確認點，其他事我會自己判斷、自己修正、自己往下做。

① Local-first — everything runs on this machine unless it truly can't; cloud AI is a last resort, and I'll say so before using it. ② Accuracy over speed — as long as you can't feel the delay, pick the more accurate option. ③ You see it before it touches your computer — the only checkpoint; everything else I judge, fix, and drive forward myself.
