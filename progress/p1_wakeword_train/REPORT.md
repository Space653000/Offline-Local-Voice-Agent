# 中文喚醒詞訓練報告——「嗨小助理」

**結論**：✅ 可用的 v0.2 自訓練中文喚醒詞模型，**88.5%** 真實端到端準確率（走正式部署路徑測試，非捷徑評估）。

## v0.2 更新（補真實環境噪音負樣本）

接上真麥克風做即時監聽煙霧測試時，發現一個 v0.1 沒抓到的問題：**對著空無一人的房間，喚醒詞會誤觸發**（信心度0.89）。
查了才發現房間其實很安靜（真實錄音RMS只有0.48，接近純靜音），但訓練時的「靜音」負樣本用的是 `np.zeros()` 純數位靜音，
跟真實麥克風錄到的環境噪音統計特性不一樣——模型沒看過「真實世界的安靜」長什麼樣子。

修法：直接用麥克風錄15秒真實環境音當額外負樣本，重新訓練。結果：
- 真實部署路徑準確率 73.1% → **88.5%**
- 一般語句正確不觸發率 13/15(87%) → **15/15(100%)**
- 近似混淆詞正確不觸發率 1/5(20%) → 3/5(60%)
- 重新跑12秒真實麥克風監聽煙麵測試：**沒有再誤觸發**

這個發現很重要：**光是加15秒真實環境錄音，比之前調整訓練演算法本身的效果還明顯**，印證了喚醒詞品質主要被資料多樣性卡住，不是模型架構問題。

## 背景：為什麼這件事本來被認為做不到

P0/P1 階段確認 openWakeWord 的**官方訓練流程**依賴 PyTorch，而 torch 當時在這台 ARM64 Windows 機器上完全沒有 wheel。使用者說「只有這台電腦」，不接受借用其他機器訓練。

**轉折點**：重新檢查發現 **PyTorch nightly 現在有 ARM64 Windows wheel了**（`torch==2.15.0.dev20260916+cpu`），這是本次工程最大的環境變化。裝起來後驗證可以正常做矩陣運算，確認能用。

但官方 `openwakeword.train` 模組除了 torch，還依賴 `audiomentations`（音訊增強），而 `audiomentations` 依賴 `numba`/`llvmlite`，這兩個在 ARM64 Windows 上編譯失敗。所以**沒有直接用官方訓練腳本**，而是自己寫了一套訓練流程，只借用官方的 ONNX 特徵萃取器（`openwakeword.utils.AudioFeatures`，純 ONNX 不需要 torch）+ 自己刻的 PyTorch 分類器。

## 資料

- 正樣本：TTS合成「嗨小助理」× 3個語音（Hanhan/Yating/Zhiwei）× 5種語速 = 15個基礎樣本，另外held-out了6個（語速值訓練時沒出現過）當測試集
- 負樣本：18個近似混淆詞（「嗨小主理」「還小助理」等發音相近但不同的詞）+ 借用 P1 的103句一般中文語句（80句訓練、23句held-out測試）
- 手刻資料增強（`audiomentations`裝不起來，改用 numpy 自己寫）：加白噪音、音量擾動、時間平移

## 過程中抓到並修正的三個真實bug（不是憑空猜的，每個都有實測證據）

### Bug 1：`embed_clips` 批次處理的 shape 不符
`AudioFeatures.embed_clips()` 內部批次計算 `n_frames = ceil(samples/160-3)`，在特定音檔長度下跟實際輸出的 frame 數量對不上，直接報 shape mismatch。改用底層單筆方法繞開（後來又因為下一個bug再改成完全串流方式）。

### Bug 2：ONNX 匯出「假成功」，數值跟原模型不一致
第一次訓練，內部驗證（PyTorch原模型）顯示98%準確，但真正走 `openwakeword.Model` 部署路徑推論只有46%，幾乎等於亂猜。追查發現新版 `torch.onnx.export`（dynamo=True 預設）匯出時觸發了 opset 版本轉換失敗警告，**匯出的 ONNX 檔案跟原本訓練好的 PyTorch 模型行為不一致**。改用 `dynamo=False`（舊版 TorchScript 匯出器）解決，並且**在匯出後立刻用同一批輸入比對 PyTorch 跟 ONNX 的輸出數值，確認最大差異=0.000000才繼續**——這個一致性檢查現在是流程的固定一步，不會再發生「匯出成功但內容跑掉」卻沒發現的狀況。

### Bug 3：模型學到「串流位置」而不是「內容」的假相關（最隱蔽的一個）
修好Bug 2後重測，發現部署路徑推論還是只有23%，比修之前更糟。仔細拆解每個時間窗格的分數才發現：模型對「任何音檔剛開始的前1秒」都給高分，不管內容是不是喚醒詞。根因是正樣本都是從音檔第0秒開始的短句（1.5-2秒），負樣本卻是完整3-4秒的長句，**串流位置本身變成了一個學得到但錯誤的判斷依據**。而且第一版內部驗證剛好用稀疏等間距抽樣負樣本視窗，很少抽到負樣本開頭那段，才會讓這個問題被漂亮的假數字蓋過去。

修法：正樣本前面加一段隨機長度（0.3-2秒）的雜訊前導，明確把「還在前導區」的視窗標成負樣本、「前導結束後、喚醒詞內容應該完整落在lookback窗格內」的視窗才標成正樣本；負樣本改成密集取樣（不再稀疏抽樣，含開頭）。修完後部署路徑準確率從23%跳到73.1%。

## 最終結果（走真正的 `openwakeword.Model.predict()` 部署路徑，逐個chunk餵，取整段最高分）

| 類別 | 結果 |
|---|---|
| 正樣本（喚醒詞，held-out語速）| 5/6 正確觸發（83%）|
| 近似混淆詞（發音相近但不同）| 1/5 正確不觸發（20%）——**明顯弱項** |
| 一般中文語句（held-out）| 13/15 正確不觸發（87%）|
| **總計** | **19/26 = 73.1%** |

## 誠實的限制

1. **近似混淆詞辨別能力不足**：「嗨小主理」「還小助理」這類發音相近的詞很容易被誤判成喚醒詞本身。原因很直接——訓練資料只有15個基礎正樣本、18個混淆負樣本，樣本量對於學會精細的音素級區分來說太少。
2. **只用3種TTS語音**，沒有真人錄音，實際使用時真人講話的音色/口音變化這個模型可能沒見過，實際準確率可能比這裡測的更低。
3. 這是 **v0.1 堪用版本**，不是生產級品質。建議：(a) 如果要提升，最有效的方法是收集更多樣化的正樣本（不同語速/音量/情境噪音，最好有真人錄音）；(b) 短期實用做法——調高觸發閾值、或喚醒詞觸發後加一道「ASR+LLM二次確認這句話真的是要喚醒助理」的關卡，用 P1/P2 已經做好的能力來補強這裡的弱點，而不是無限打磨喚醒詞本身。
