# 中文 ASR 模型選型實測報告

**測試方式**：103 句繁體中文語音助理常見指令（開瀏覽器、調音量、行事曆、Git 操作等），用 Windows 內建
SAPI5 神經語音（Microsoft Hanhan，zh-TW）合成成 16kHz 單聲道 WAV，餵給 whisper.cpp（CUDA GPU 版）
四個不同大小的多語言模型（tiny/base/small/medium），量測辨識準確率與延遲。

> **重要限制說明**：測試音檔是 TTS 合成的乾淨語音，不是真人講話（沒有背景噪音、口音、麥克風品質問題）。
> 實際使用時各模型的絕對準確率會比這裡低，但**模型之間的相對排名跟速度數據仍然有參考價值**。

## 結果總表

| 模型 | 檔案大小 | 字元錯誤率 CER（簡繁正規化後） | 句子完全正確率 | 平均延遲/句 | 即時率 RTF |
|---|---|---|---|---|---|
| tiny | 77.7 MB | 16.6% | 38.8% | 0.41s | 0.15 |
| base | 148.0 MB | 10.1% | 65.1% | 0.46s | 0.17 |
| **small** | 487.6 MB | **5.9%** | 75.7% | **0.77s** | 0.29 |
| medium | 1533.8 MB | 2.1% | 90.3% | 1.61s | 0.60 |

（RTF = 處理時間 / 音檔長度，< 1 代表比即時說話還快；GPU：RTX Spark CUDA）

## 關鍵發現

1. **whisper 多語言模型有簡繁混雜的怪癖**：同一個模型偶爾吐「打开浏览器」（簡體）偶爾吐「關掉這個視窗」（繁體），內容完全正確但字形不一致。第一輪測試沒處理這個問題，導致 small 模型的原始 CER（24.2%）看起來比 base（10.9%）還差——這是誤判，不是模型真的變差。加上簡繁正規化（OpenCC s2t）之後排名才恢復正常（tiny < base < small < medium，準確率遞增），數字才可信。
   → **實作上的啟示**：正式系統的 ASR 輸出後面要接一道「簡轉繁」正規化，不能直接信任模型輸出的字形。
2. **句子完全正確率（含標點）比字元錯誤率嚴格很多**：medium 都只有 90.3% 完全正確，主要是模型會自己加標點符號（「。」「？」）跟原句不同。但對下游 LLM 做意圖理解來說，多一個句尾標點基本不影響語意判斷，所以**字元錯誤率是比較合理的參考指標**，完全正確率是比較嚴格的上限。
3. **延遲跟準確率是明確的 trade-off**，且都在 GPU 上跑：
   - `tiny`/`base` 延遲都在 0.5s 內，但 CER 都兩位數（10~17%），對語音指令這種容錯度低的場景偏危險
   - `medium` 準確率最好（CER 2.1%），但平均延遲 1.6s，已經超過藍圖 P6 訂的「喚醒→ASR < 1.5秒」目標，扣掉 VAD/喚醒詞/傳輸的時間後幾乎沒有餘裕
   - `small` 是目前看起來最平衡的選擇：CER 5.9%（接近藍圖「>95%辨識成功率」的門檻）、延遲 0.77s，留給 VAD+喚醒詞+LLM 推論足夠的時間預算

## 建議（已依使用者指示修正：精準度優先於速度）

使用者明確要求「精準度比速度重要，速度只要人感覺不到延遲就可以」，因此改採：

**正式採用 `ggml-medium.bin`（多語言版）作為 P1 的 ASR 模型**，理由：
- 準確率最高（CER 2.1%，簡繁正規化後句子級完全正確率 90.3%），這是使用者的第一優先
- 平均延遲 1.61s——單看 ASR 這一步確實超過藍圖原訂的「喚醒→ASR < 1.5秒」，但對「人感覺不到延遲」這個較寬鬆的標準來說可以接受（一般對話式回應的可接受延遲門檻約 2~3 秒），使用者已確認這個取捨可以接受
- 之後若整條 pipeline（VAD+喚醒詞+ASR+LLM+TTS）疊加後總延遲太長，可以再評估串流式解碼（不用等整句講完才開始轉錄）來壓低 medium 的實際感受延遲，而不是退回犧牲準確率換速度
